## 0. Why Phase 3 Is Mostly Not Code

Phases 1 and 2 shipped the full F1–F8 feature set from PRD §5.1. Every script the V1 architecture calls for now exists. Internal tools, per PRD §8.2 / §10, **earn their keep through use, not through pre-build review**. The remaining V1 risk is not "is the code correct" — it's "does the pipeline survive contact with a second, non-test-rig prospect."

Phase 3 is therefore a **validation phase**: run the full pipeline end-to-end against a real second prospect, treating any breakage as a forcing function for a small targeted patch, then declare V1 shipped.

This is the phase that closes PRD §7's last unresolved acceptance criterion:

> ☐ Claude+Nia MCP queries return cited responses — Test query against `/v2/search mode=universal`: "what's the strongest outreach angle for {founder}?" returns specific cites

design_doc §7 step 8 also requires the operator-side test to be a **second prospect, not James**.

## 2. Phase 3 Mission

Run kaide-recon end-to-end on a **second real prospect**, prove the Claude+Nia MCP querying loop returns cited outreach angles, and patch any small breakages real-world contact reveals. After Phase 3, V1 is shipped — Hafeedh starts using kaide-recon as the actual sales tool, not a test rig.

Three deliverables:

1. **D1 — Second-Prospect Dossier**: a real, committed `dossiers/<slug>/dossier.md` for a prospect that is not James He. Same 7-section structure, same citation discipline, generated by the unmodified Phase 1+2 pipeline.
2. **D2 — MCP Query Validation Log**: a short markdown file at `decisions/phase_3_mcp_validation.md` capturing the actual Claude+Nia MCP session output: the query, the universal search call shape, the angles returned, whether they cited specific public statements. Proof that PRD §7's last unresolved checkbox is closed.
3. **D3 — Phase 3 Retrospective**: `decisions/phase_3_decisions.md` capturing exactly what broke during the second-prospect run, what was patched, and what was deferred. **Patches are allowed but must be minimal** — see §5.

## 4. Execution Sequence (Operator-Driven, Agent-Assisted)

Phase 3 is operator-led — the execution agent assists with file ops, patches, and writing the validation log, but Hafeedh drives the actual run because the run involves manual LinkedIn capture, Claude+Nia MCP session interaction, and a $5+ Max API call. The agent must not start the run unprompted.

### 4.1 Pre-flight (agent self-check)

1. Run `python scripts/validate_pipeline.py`. Confirm PASS (warns acceptable).
2. Confirm `git status` is clean. If dirty, commit or stash before the run.
3. Read the operator's stated prospect name + company. Compute slug. Confirm `dossiers/<slug>/` does not yet exist (a half-finished prior attempt would conflate the validation).

### 4.2 The run (operator drives, agent narrates / patches)

```
1. python scripts/orchestrate.py "<Founder>" "<Company>" [twitter_handle]
2. [Operator manual] LinkedIn PDF + activity screenshots → raw/linkedin/
3. python scripts/research.py "<Founder>" "<Company>" "dossiers/<slug>/raw"
   (5s cost gate; ~15 min wall-clock; ~$5 spend)
4. Operator reviews dossier.md. If unusable, halt — do not paper over poor synthesis.
5. git add dossiers/<slug>/dossier.md && git commit && git push
6. python scripts/index_to_nia.py repo "<gh-user>/kaide-recon" master
   (and optional founder/company repos + docs site)
7. [Operator manual] Open Claude with Nia MCP attached.
   Run: python scripts/query_dossier.py "<Founder>" "<Company>" | clip
   Paste into Claude. Read the angles. Capture the session output verbatim.
```

### 4.3 Post-run (agent writes the validation log)

The agent creates `decisions/phase_3_mcp_validation.md` containing:

- **Header**: prospect name, slug, run date.
- **Section 1 — The Query**: the exact prompt that went into Claude.
- **Section 2 — The MCP Call**: the `/v2/search` body shape that Claude actually sent (extracted from Claude's MCP tool-call output).
- **Section 3 — The Response**: the 3 ranked outreach angles Claude produced, **with the source URLs they cited**. If any angle has no citation, that's a validation failure for PRD §7 — flag it.
- **Section 4 — Verdict**: one of `PASS` / `PASS_WITH_NOTES` / `FAIL`. Criteria:
  - PASS: 3 angles, each cites at least one specific public statement (URL or paraphrase with attribution), at least 1 angle references a Kaide-Labs-relevant bottleneck (hiring spike, integration commitment, enterprise pain).
  - PASS_WITH_NOTES: above conditions met but with caveats (e.g., one angle is generic, citations are paraphrased not URL'd).
  - FAIL: no angle cites a specific public statement, or angles are generic "we help you scale" content. Triggers a prompt-tuning patch — see §5.2.

### 4.4 Cost ledger

The agent records, in `decisions/phase_3_decisions.md`, the actual run costs:

| Item | Estimated | Actual |
|---|---|---|
| Deep Research Max | ~$5 | TBD |
| Flash routing (orchestrate doesn't call route per-artifact in Phase 1; only `repitch.py` does — likely $0 for first-time pitch) | $0 | TBD |
| Files API uploads | $0 | $0 |
| Nia indexing | $0 | $0 |
| **Total per-prospect** | **~$5** | TBD |

If actual > $15, that's a PRD §3 hard-constraint violation — halt and flag for Hafeedh.

If actual is in the $5-15 range, that's within budget but worth noting in the retrospective so future-Hafeedh knows what a real run costs.

## 5. Allowed Patch Scope (§3 / Anti-Scope Carve-Out)

Phase 3's whole point is "iterate on real use." Patches are explicitly allowed, but **only** when the second-prospect run forces the issue. Speculative refactors are still banned.

### 5.1 Patches the agent may apply autonomously

If the second-prospect run reveals one of the following, the agent may patch it without escalation:

| Symptom | Allowed patch |
|---|---|
| A `gather_*.py` 404s on a specific selector / URL pattern that worked for James | Update the selector or URL template in that single file. Note in `decisions/phase_3_decisions.md`. |
| `route.py` returns malformed verdicts on the second prospect's delta artifacts | Tighten the `prompts/router_prompt.md` rubric (append a "RETURN FORMAT" reminder). Don't rewrite the rubric. |
| `research.py` Files API upload fails on a previously-untested file extension | Add the extension to `ALLOWED_EXTENSIONS` if it's a clearly-text format (e.g., `.json` for HN export). Do not add binary types. |
| `index_to_nia.py` 4xx for a payload shape Nia changed | Update the body to match the current `/v2/sources` schema. Verify against `docs.trynia.ai` indexed in Nia. Cite the change in decisions. |
| `validate_pipeline.py` reports a false FAIL | Loosen the check to a WARN, never silently delete it. |

### 5.2 Patches that require Hafeedh sign-off (HALT and flag)

| Symptom | Why it requires sign-off |
|---|---|
| Claude+Nia MCP query returns generic/uncited angles | Suggests `prompts/deep_research_prompt.md` or `kaide_labs_positioning.md` needs tuning. Prompt edits are strategic — Hafeedh decides. |
| Cost per run > $15 | PRD §3 hard constraint violation. |
| Active human time per run > 30 min | PRD §3 hard constraint violation. |
| Deep Research Max model is deprecated / rejected | Stack lock change — design_doc §1.1 must be updated by Hafeedh. |
| Nia v2 endpoint shape changed in a way that breaks `/v2/sources` or `/v2/search mode=universal` | Architectural — design_doc §9 changes are Hafeedh's call. |
| Output dossier is unusable for outreach drafting (PRD §7 row 4) | Synthesis pipeline isn't earning its keep — strategic question, not a code bug. |
| Manual LinkedIn capture is friction-heavy enough to push total time over budget | Strategic; PRD §8.1 LinkedIn rule is locked, but capture protocol may need rethinking. |

### 5.3 Permanently banned in Phase 3

- Adding any V1.1 / V2 deferred feature.
- Adding pip dependencies.
- Refactoring across files (single-file targeted fixes only).
- Changing `model IDs` or endpoint paths without explicit Hafeedh approval.
- Touching `linkedin.com` programmatically. Still banned. Always banned.
- Auto-sending the outreach drafts Claude generates.

## 6. Phase 3 Acceptance Test (V1 Ship Gate)

Phase 3 — and V1 — are done when **all** are true:

| ✓ | Criterion | Verification |
|---|---|---|
| ☐ | A second prospect's `dossier.md` exists, committed to `master`, with all 7 required headings | `git ls-files dossiers/ \| grep dossier.md` shows ≥ 2 |
| ☐ | Run cost ≤ $15 | Recorded in `decisions/phase_3_decisions.md` |
| ☐ | Active human time ≤ 30 min | Recorded in `decisions/phase_3_decisions.md` |
| ☐ | `decisions/phase_3_mcp_validation.md` exists, verdict is `PASS` or `PASS_WITH_NOTES` | File exists, verdict line present |
| ☐ | Each of the 3 angles in the MCP response cites a specific public statement | Captured in §3 of the validation log |
| ☐ | No raw LinkedIn artifacts leaked into the repo | `git ls-files dossiers/ \| grep linkedin/` returns empty |
| ☐ | `validate_pipeline.py` still PASS after the run (no regressions) | Re-run post-run |
| ☐ | All Phase 3 patches (if any) are documented in `decisions/phase_3_decisions.md` with the symptom + the change | File exists |
| ☐ | No PRD §3 hard constraint violated | Reviewed in retrospective |
| ☐ | The Phase 3 retrospective explicitly states either "V1 SHIPPED" or "V1 BLOCKED ON: <reason>" | Final line of `decisions/phase_3_decisions.md` |

If verdict is `FAIL` on D2, **do not** loop on prompt-tuning autonomously — that's strategic. Halt, flag, hand back to Hafeedh.

## 7. Anti-Scope (Reinforced)

1. Do not run Phase 3 against James (he's already validated).
2. Do not run Phase 3 against more than one new prospect. One real second-prospect run is the gate; subsequent prospects are post-V1 production use.
3. Do not auto-pick the prospect. Operator names the target.
4. Do not auto-send outreach. The MCP-generated drafts are reviewed and sent by Hafeedh.
5. Do not write `previous_interaction_id` chaining "while we're at it."
6. Do not refactor `orchestrate.py` or `repitch.py` to share code "while we're at it."
7. Do not generalize the pipeline to non-B2B-AI prospects (PRD §12.4).
8. Do not add a CHANGELOG, CONTRIBUTING, LICENSE, or any other file the spec doesn't list. Repo hygiene is fine as-is.
9. Do not push `decisions/phase_3_*.md` files until the run is actually complete. Half-finished retrospectives are worse than no retrospective.
10. Do not retry a `failed` Deep Research Max run automatically — that's $5 of opaque burn. Halt and flag.
